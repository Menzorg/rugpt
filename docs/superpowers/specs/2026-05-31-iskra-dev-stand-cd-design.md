# Дизайн: дев-стенд ИСКРЫ + CD-пайплайн из ветки `dev`

Дата: 2026-05-31. Статус: согласован, к реализации.

## Цель

Поднять дев-стенд на контейнере `rag-dev` (Proxmox) и настроить деплой движка и
вебклиента туда из ветки `dev` каждого репозитория через GitLab CI.

## Топология

- **rag-dev** — контейнер Proxmox, голая Ubuntu. Будет Docker-хостом.
  - ssh снаружи: `217.113.118.218:20935`, юзер `rugptdev`, ключ `~/.ssh/rugptdev_petr` (Omada-проброс).
  - внутренний IP в `192.168.1.0/24` — уточнить при провижене (`hostname -I`).
- **rag-worker** — VM с раннером `MainWorker` (shell executor). Деплоит на `rag-dev`
  **по локалке** (внутренний IP), не через NAT.
- **rag-gitlab** (`192.168.1.118`) — GitLab, репозитории `iskra/engine`, `iskra/webclient`.

## Принятые решения

- Деплой — **вариант B (push-rsync)**: раннер `rsync`-ит свой git-чекаут на `rag-dev`,
  затем по ssh запускает рестарт. По сути существующий `deploy.sh` с `SERVER=rag-dev`.
- **Движок** на rag-dev — **venv+screen на хосте** (как на проде), не в Docker.
- В **Docker** на rag-dev — только зависимости и вебклиент.
- `.env` — **файл на rag-dev**, в репозиторий/CI не попадает (rsync его исключает).
- Существующий (падавший) `.gitlab-ci.yml` — **редактируем**, заменяя содержимое
  деплой-пайплайном. CI/CD проекта не выключаем.

## Этап 1 — дев-стенд

### Зависимости в Docker (compose, порты публикуются на хост)

| Сервис | Образ | Порт на хост |
|---|---|---|
| PostgreSQL + pgvector | `pgvector/pgvector:pg16` | 5432 |
| Redis | `redis` | 6379 |
| Kafka | из `docker-compose.kafka.yml` репо | 9092 |
| Вебклиент (2 контейнера) | из compose репо `iskra/webclient` | 3000 / 4000 |

pgvector обязателен — движок использует его для RAG (миграции делают `CREATE EXTENSION`).

### Движок на хосте

1. Клон `iskra/engine` в `~/rugpt`, Python venv, `pip install -r requirements.txt`.
2. `.env` (вручную, из `.env.example`): БД/Redis/Kafka → `localhost:<порт>` (контейнеры
   публикуют порты на хост), LLM → `192.168.1.80:4000`.
   - **`API_HOST=0.0.0.0`** (не 127.0.0.1) — чтобы контейнеры вебклиента доставали движок
     через `host.docker.internal`.
3. Миграции + первый старт: `./local_restart.sh engine` (он сам: миграции → screen → health-check `:8100/api/v1/health`).
4. Завести ветку **`dev`** (protected) в `iskra/engine`.

### Доступ к дев-вебклиенту

Как девы открывают UI дев-вебклиента (ssh-туннель как к GitLab, или порт на локалку) —
решается при провижене вебклиента. На схему деплоя не влияет. (Открытый пункт.)

## Этап 2 — пайплайн

Оба репозитория получают ветку `dev` (protected) и свой `.gitlab-ci.yml` с job'ом деплоя,
триггер только на `dev` (`rules: if $CI_COMMIT_BRANCH == "dev"`). Раннер — существующий
`MainWorker`.

Шаги job'а (общие, вариант B):
1. поднять ssh-ключ из protected file-переменной `DEV_SSH_KEY`;
2. `rsync` чекаута → `rag-dev:<путь>` (исключая venv/.env/logs/uploads/.git/__pycache__);
   для движка — отдельно зеркало `migrations/` с `--delete`;
3. (движок) pip install при изменении `requirements.txt`;
4. рестарт по ssh.

### Различия движок / вебклиент

| | Движок | Вебклиент |
|---|---|---|
| Путь на rag-dev | `~/rugpt` | `~/webclient` |
| Рантайм | venv+screen на хосте | Docker (2 контейнера) |
| Рестарт в CI | `./local_restart.sh engine` | `docker compose build && docker compose up -d` |
| Env на rag-dev | `.env` | `.env` + `packages/backend/.docker.env` |

Фронт вебклиента **пересобирается** (`build`), т.к. `NEXT_PUBLIC_*` зашивается на этапе сборки.

### Секреты и доступ

- **`DEV_SSH_KEY`** — приватный ключ раннер→`rag-dev`, как **protected file-переменная**
  в GitLab CI/CD. Публичная половина — в `authorized_keys` юзера `rugptdev` на `rag-dev`.
- Ветка `dev` — **protected**, чтобы protected-переменная отдавалась только на ней.
- Раннер и rag-dev: на обоих нужен `rsync` (доставить, если нет).

## Порядок реализации

1. Дев-стенд движка (Docker-зависимости + venv + .env + первый запуск).
2. Пайплайн движка (ssh-ключ, ветка `dev`, `.gitlab-ci.yml`, тестовый деплой).
3. Вебклиент тем же шаблоном (стенд + пайплайн).
