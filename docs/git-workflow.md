# Git Workflow (ветки и релизы)

Модель ветвления команды RuGPT. Описывает, как фича проходит путь от разработки до
прода и какую роль играет каждая постоянная ветка.

> Заменяет устаревшую схему `feature → dev → MR dev→main` из
> `collaborative-development.md`. Целевая ветка готового кода — **`release`**, а не `dev`.

---

## Постоянные ветки

| Ветка | Роль | Защита |
|---|---|---|
| `main` | Прод. Только проверенный, выкатанный код. | Защищена — прямой push запрещён, только MR с approval |
| `release` | «Готовое и рабочее». Накопитель зрелых фич перед выходом в прод. От неё ветвятся фичи. | Защищена — только MR |
| `dev` | **Одноразовая интеграционная ветка** для теста на dev-сервере. Регулярно обнуляется от `release`. | **Не защищена** — разрешён force-push |

Ключевой принцип: **`dev` ничего не «хранит»**. Это площадка для прогона фич на dev-сервере.
Вся ценность живёт в feature-ветках и в `release`. Содержимое `dev` в любой момент
выбрасывается и пересоздаётся от `release`.

## Жизненный цикл фичи

```
1. Разраб ветвит фичу от release:
   git checkout release && git pull
   git checkout -b feature/my-feature

2. Пилит. Чтобы потестить на dev-сервере — мерджит фичу в dev:
   git checkout dev && git merge feature/my-feature && git push

3. Смотрит на dev-сервере. Нужны правки — делает их В СВОЕЙ feature-ветке
   (не в dev!) и снова мерджит в dev. Повторяет, пока фича не заработает как надо.

4. Фича готова и проверена → мерджит ЕЁ в release (через MR):
   feature/my-feature → release

5. release → main (через MR с approval) → CI деплой на прод.
```

Схема:
```
        ┌──────────── ветвление ────────────┐
        ▼                                    │
   feature/* ──merge──► dev (тест на dev-VM, итерации)
        │
        └──MR (готовое)──► release ──MR──► main ──► prod
```

## Правила

1. **Готовую фичу мерджат в `release`, а не из `dev`.** В `dev` фича попадает только
   для прогона. Мердж `dev → release` или `dev → main` **запрещён** — `dev` грязный
   по определению (в нём чужие недозревшие фичи).

2. **`release` и `main` защищены** — push только через Merge Request. Прямой
   `git push origin main` отлетит с `pre-receive hook declined`.

3. **`dev` не защищаем** — обнуление переписывает историю, нужен force-push.

## Обнуление dev от release

`dev` периодически «обнуляется» — выбрасывается накопленное и пересоздаётся от `release`:

```bash
git checkout dev
git fetch origin
git reset --hard origin/release
git push --force-with-lease origin dev
```

- `--force-with-lease` безопаснее голого `--force`: отклонится, если кто-то запушил
  в `dev` без твоего ведома.
- Ничего не теряется: всё готовое уже в `release`, а незрелое — в feature-ветках.

### После обнуления — синк у остальных разработчиков

`dev` переписан, поэтому локальный `dev` синкают **жёстким сбросом, а не `git pull`**
(иначе ловишь merge-кашу из разъехавшихся историй):

```bash
git fetch origin
git checkout dev
git reset --hard origin/dev
```

## Подвох: тест поверх чужих фич

Фича в `dev` тестируется поверх **других** недозревших фич, которые там тоже накопились.
Когда фича поедет в `release`, этих соседей рядом не будет — может всплыть конфликт или
поведение, которого на `dev` не наблюдалось.

Поэтому **перед мерджем фичи в `release`** имеет смысл прогнать её на чистом `dev`
(`release` + только эта фича), чтобы проверить в изоляции:

```bash
git checkout dev
git reset --hard origin/release
git merge feature/my-feature
git push --force-with-lease origin dev
# прогнать на dev-сервере; если ок — фичу в release
```
